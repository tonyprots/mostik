# Выпуск Mostik: подпись, .dmg, лента, автообновление

Как из репозитория получить `.dmg`, который ставится на чужой Mac и потом сам обновляется через Sparkle 2, и как его опубликовать. Собирает `scripts/release.sh`, он ничего не публикует. Публикует `scripts/publish-release.sh`: по умолчанию это сухой прогон, публикация — только с подтверждением.

Подпись по умолчанию — **самоподписанный сертификат «Mostik Release»**. Developer ID не нужен. Режим Developer ID (`--developer-id`) остаётся рабочим и включится, когда появится аккаунт Apple.

## Что нужно сопровождающему

| Что | Зачем | Где взять |
|---|---|---|
| Сертификат «Mostik Release» с закрытым ключом в связке «Вход» | подпись приложения: по нему macOS узнаёт Mostik в разрешениях | создать один раз, раздел «Сертификат „Mostik Release“» ниже |
| SHA-1 сертификата в `release/release.conf` | закрепляет именно этот сертификат: `release.sh` не подпишет другим | `security find-certificate -c "Mostik Release" -Z \| grep SHA-1` |
| Резервная копия `.p12` и ключа EdDSA | без них установленные копии не примут ни одного обновления | раздел «Резервная копия» ниже |
| Ключ EdDSA (`app.mostik.mac`) в связке «Вход» | подпись `.dmg` и ленты для Sparkle | уже создан, раздел «Что уже сделано» |
| Репозиторий `tonyprots/mostik` на GitHub с включёнными Pages из ветки `gh-pages` | Releases хранят `.dmg`, Pages отдают ленту `https://tonyprots.github.io/mostik/appcast.xml` | раздел «GitHub: репозиторий и Pages» ниже |
| `gh`, вошедший в `tonyprots` | `publish-release.sh` создаёт Release и пушит ленту | `gh auth login` |

Адрес ленты и репозиторий записаны в одном месте — `release/release.conf`. Адрес ленты после выпуска 0.1.0 **не меняется никогда**: установленные копии знают только его. Переезд на свой домен — перенаправлением со старого адреса.

## Что уже сделано

- **Sparkle 2.10.0** скачан с GitHub Releases в `vendor/sparkle/2.10.0/`, ссылка `vendor/sparkle/current`, архив — `vendor/sparkle/dl/`. Сумма SHA-256 архива совпала с опубликованной на странице релиза; полная сумма закреплена в `scripts/vendor.lock`, и `release.sh` сверяет с ней архив и распакованную папку. `vendor/` в `.gitignore`: бинарники в git не кладём.
- **Ключ EdDSA** создан `generate_keys --account app.mostik.mac`. Закрытый ключ лежит только в связке ключей «Вход» (элемент с учётной записью `app.mostik.mac`), нигде не напечатан и не закоммичен. Публичный — `SUPublicEDKey` в `Resources/Info.plist`. Посмотреть публичный: `vendor/sparkle/current/bin/generate_keys --account app.mostik.mac -p`.

## Сертификат «Mostik Release»

Создаётся **один раз** и живёт ~10 лет. Агенты сертификат не создают и в связку ключей не импортируют — это делает сопровождающий руками.

1. «Связка ключей» (`/System/Library/CoreServices/Applications/Keychain Access.app`) → меню «Связка ключей» → «Ассистент сертификации» → «Создать сертификат…».
2. Имя: `Mostik Release` (ровно так: `release.sh` ищет сертификат по имени из `release/release.conf`). Тип удостоверения: «Самоподписанный корневой». Тип сертификата: **«Подпись кода»**. Поставить галочку «Переопределить стандартные значения» → «Продолжить».
3. Срок действия: **3650** дней. Остальные шаги — по умолчанию; связка — «Вход».
4. Доверие сертификату менять **не нужно**: для подписи хватает того, что он есть, а системное доверие только расширило бы, чему верит Mac.
5. Записать SHA-1 в `release/release.conf`:
   ```bash
   security find-certificate -c "Mostik Release" -Z | grep SHA-1
   ```
   Строку `MOSTIK_SIGN_CERT_SHA1=` дополнить 40 знаками без пробелов и закоммитить.
6. Проверить: `security find-identity -p codesigning | grep "Mostik Release"` показывает тот же SHA-1 (без `-v`: «не доверенный» для самоподписанного — это нормально).

Требование подписи (designated requirement) каждой сборки — `identifier "app.mostik.mac" and certificate leaf = H"<SHA-1>"`. Оно одно для всех версий, поэтому разрешения (микрофон, Универсальный доступ, «Запись экрана», звук системы) после обновления остаются. **Новый сертификат = все установленные копии теряют разрешения**, а сам Mostik откажется ставить такое обновление и объяснит почему. Поэтому сертификат не пересоздаётся, а восстанавливается из резервной копии.

## Резервная копия

Два секрета, без которых выпуск невозможен: сертификат с закрытым ключом (`.p12`) и ключ EdDSA. Оба хранятся только в зашифрованном виде, рядом друг с другом. Открытым текстом на диске их не держать даже временно — ни в домашней папке, ни в «Загрузках», ни в репозитории.

1. Дисковая утилита → «Файл» → «Новый образ» → «Пустой образ»: имя `mostik-release-keys`, 50 МБ, шифрование **AES-256**, длинный пароль (в менеджер паролей). Подключить образ.
2. Сертификат: «Связка ключей» → «Мои сертификаты» → «Mostik Release» (с треугольником, внутри закрытый ключ) → правый клик → «Экспортировать…» → формат «Обмен личной информацией (.p12)» → сохранить **прямо в подключённый образ** → задать пароль `.p12` (тоже в менеджер паролей).
3. Ключ EdDSA — туда же:
   ```bash
   vendor/sparkle/current/bin/generate_keys --account app.mostik.mac -x /Volumes/mostik-release-keys/mostik-sparkle-key.txt
   ```
4. Отключить образ. Сам `.dmg` образа положить в два места: например, в облако и на внешний диск.

Восстановление на новой машине: подключить образ; двойной клик по `.p12` → связка «Вход»; `generate_keys --account app.mostik.mac -f /Volumes/mostik-release-keys/mostik-sparkle-key.txt`; отключить образ. SHA-1 после восстановления тот же.

## GitHub: репозиторий и Pages

Один раз, до первого `publish-release.sh --publish`:

1. Создать репозиторий `tonyprots/mostik` (публичный: Pages и Releases бесплатного аккаунта отдают файлы публично).
2. Запушить код; ветку `gh-pages` создавать не нужно: первая публикация сделает её сама (сирота, с `.nojekyll`).
3. После первой публикации: Settings → Pages → Source «Deploy from a branch» → `gh-pages`, папка `/ (root)`. Проверить, что `https://tonyprots.github.io/mostik/appcast.xml` открывается. Скрипт проверяет Pages сам (`gh api repos/tonyprots/mostik/pages`) и без них остановится, но на самый первый раз ветки ещё нет — включить Pages можно только после неё.

## Как устроено

**Sparkle без Xcode.** Фреймворк не линкуется: `SparkleUpdater` (`Sources/MostikKit/SparkleUpdater.swift`) грузит `Contents/Frameworks/Sparkle.framework` в рантайме и создаёт `SPUStandardUpdaterController`. Поэтому `swift build`, `swift run` и CI собираются без `vendor/sparkle`, а выпуск получает стандартные окна Sparkle. Когда можно запускать Sparkle, решает `UpdatePolicy` в ядре (покрыт тестами): фреймворк на месте, лента не заглушка и https, ключ 32 байта.

**Проверка обновлений всегда включена.** Ни вопроса при первом запуске, ни переключателя в Настройках: в Настройках — строка о том, что раз в день уходит на сервер (номер версии и адрес компьютера). Режим установки — **по кнопке**: Sparkle показывает окно «Доступна новая версия», ставит после «Установить». Галочка Sparkle «Автоматически загружать и устанавливать обновления» в том же окне остаётся — кто хочет, включает её. По умолчанию по кнопке, потому что после установки Mostik перезапускается, а запись разговора обрывать нельзя; перезапуск и так ждёт, пока идёт запись или встреча (`SparkleUpdateGuard`).

**Требование подписи в ленте.** Sparkle принимает обновление по верной подписи EdDSA и смену сертификата пропускает. Поэтому `release.sh` пишет требование подписи сборки в элемент ленты (`<mostik:designatedRequirement>`, пространство имён `urn:app.mostik:appcast`), а `SparkleUpdateGuard` (`updater:shouldProceedWithUpdate:updateCheck:error:`) сравнивает его с требованием установленной копии. Не совпало или в ленте его нет — обновление не ставится: при проверке по кнопке — ошибка в окне Sparkle, при фоновой — одно окно на версию с объяснением, какие разрешения пришлось бы выдать заново, и советом поставить `.dmg` руками, если это ожидаемо.

**`scripts/bundle.sh`** кладёт фреймворк в `Contents/Frameworks`, если есть `vendor/sparkle/current` (или `MOSTIK_SPARKLE`). Нет — сборка идёт без автообновления, с предупреждением.

**`scripts/release.sh`** — режимы `--self-signed` (по умолчанию), `--developer-id`, `--adhoc`. По шагам:

1. Проверка. Адрес ленты и репозиторий — только из `release/release.conf`, `MOSTIK_FEED_URL` в окружении — остановка. Self-signed: SHA-1 закреплён (пусто — остановка с инструкцией, код 2), сертификат с этим именем в связке ровно с этим SHA-1, закрытый ключ к нему есть. Developer ID: `DEVELOPER_ID`, `TEAM_ID`, профиль `notarytool`. Кроме adhoc: ключ EdDSA в связке совпадает с `SUPublicEDKey`. Затем цепочка поставки (`docs/packaging.md`, «Цепочка поставки»): `vendor_python.py verify` сверяет встроенный Python, его пакеты и Sparkle с `scripts/vendor.lock` и `scripts/requirements.lock`; незакоммиченные изменения останавливают выпуск.
2. Сборка через `bundle.sh` в `release-out/stage/` (`dist/` и запущенный Mostik не трогаются). В бандле — SBOM `Contents/Resources/MOSTIK-VENDOR.json`; отметка `"dirty": true` вне adhoc — остановка. В Info.plist копии: версия и номер сборки, `SUFeedURL` из `release.conf`, `SUEnableAutomaticChecks = true`, `SURequireSignedFeed = true`.
3. Подпись изнутри наружу (`scripts/sign-app.sh`): отдельные Mach-O (встроенный Python и его `.so`/`.dylib`, `Autoupdate`), вложенные бандлы от самых глубоких (`Downloader.xpc`, `Installer.xpc`, `Updater.app`, `Sparkle.framework`), последним — `Mostik.app` с явным требованием подписи. Self-signed — без hardened runtime и метки времени: проверка библиотек hardened runtime требует Team ID, а у самоподписанного сертификата его нет. Developer ID — hardened runtime и метка времени.
4. Сверка: требование подписи `codesign -d -r-` у собранного приложения совпадает с закреплённым (без учёта регистра хеша); `Sparkle.framework`, `Autoupdate` и встроенный `python3` подписаны тем же «Mostik Release».
5. Только Developer ID: нотаризация `.app` и скрепка.
6. `.dmg`: фон рисуется кодом (`scripts/dmg-layout.swift`), ссылка на `/Applications`, раскладка — `.DS_Store` без AppleScript. Образ — UDZO; проверка на пути и логин сборщика. Developer ID — подпись, нотаризация и скрепка образа.
7. Кроме adhoc: `sign_update` подписывает `.dmg` ключом EdDSA (подпись — рядом, `.dmg.sparkle-signature`); `scripts/appcast.py` добавляет `<item>` в `release-out/appcast.xml` (шаблон `release/appcast.xml`; та же сборка заменяется, новые — сверху) с `sparkle:minimumSystemVersion` из `LSMinimumSystemVersion` и требованием подписи; `sign_update` подписывает саму ленту, `--verify` её проверяет. Правка `appcast.xml` руками ломает подпись — только через `release.sh`.

**`scripts/publish-release.sh <версия> [--publish]`.** Без `--publish` — сухой прогон: проверяет и печатает план. Проверки: EdDSA у `.dmg` и у ленты; элемент ленты (адрес `https://github.com/tonyprots/mostik/releases/download/v<версия>/Mostik-<версия>.dmg`, длина, подпись, минимальная macOS, требование подписи); приложение в образе (смонтирован только на чтение) — та же версия, тот же `SUFeedURL`, то же требование, что в ленте, и не ad-hoc; `gh` вошёл, репозиторий есть, тега ещё нет, Pages включены. С `--publish` — подтверждение набором номера версии, затем `gh release create v<версия>` с `.dmg` и текстом из `release/release-notes.md` и раздела `CHANGELOG.md`, ожидание, пока `.dmg` скачивается, лента — коммит «Лента: Mostik <версия>» в `gh-pages` и push, ожидание, пока Pages отдают новую версию. Порядок важен: сначала `.dmg`, потом лента — иначе установленные копии пошли бы за файлом, которого ещё нет.

**Entitlements** (`release/`):

- `Mostik.entitlements` — приложение: `device.audio-input` (микрофон) и `personal-information.calendars` (календарь), они соответствуют `NSMicrophoneUsageDescription` и `NSCalendarsFullAccessUsageDescription`. Для звука системы (process tap), «Записи экрана» и Универсального доступа entitlement не нужен, их выдаёт TCC. Apple Events приложение не шлёт: Календарь и Почта открываются файлом `.ics` и ссылкой `mailto` через `NSWorkspace`.
- `Engine.entitlements` — только для исполняемых файлов встроенного Python: `cs.allow-unsigned-executable-memory` (нужен ctypes и libffi) и `cs.disable-library-validation` (для библиотек, которые пакеты распаковывают во время работы).

## Запрещённые строки

`scripts/check-denylist.sh` не пускает в репозиторий и в сборку строки из закрытого списка: названия внутренних систем, адреса, имена переменных с ключами. Сам список в репозитории не лежит, иначе он был бы утечкой:

- локально — `.git/info/denylist` (git его не публикует), по строке на подстроку, без учёта регистра;
- в CI — секрет `MOSTIK_DENYLIST` с теми же строками; без него задание `denylist` только предупреждает.

Где срабатывает: хук `.githooks/pre-commit` (`--staged`; включить один раз: `git config core.hooksPath .githooks`), задание CI `denylist` (`--tracked` и `--history`), `bundle.sh` (`--app`, без списка — предупреждение), `release.sh` (`--tracked`, `--history` и `--app` строго: без списка выпуск не собирается). Печатаются только файл:строка и хеши коммитов, ни строки из списка, ни найденный текст.

## Данные между версиями

Обновление не должно ломать то, что записала прошлая версия:

- `settings.json` несёт `schemaVersion` (`Settings.currentSchemaVersion`). Миграции — только вперёд (`SettingsMigration`): файл без версии считается версией 0. Файл новее текущей версии (откат на старую сборку) читается как есть, а незнакомые ключи при сохранении не теряются — их переносит `Settings.save`. Тест читает замороженные файлы прошлых версий из `Sources/MostikCoreTests/Fixtures/`; новая версия схемы = новая фикстура, старые не правятся.
- Манифест встречи (`manifest.json`) — `schema_version`, миграции в `meeting_folder.MIGRATIONS`, применяются при чтении (`read_manifest`, `MeetingStore.load`). Нет шага — ошибка, а не молчаливое чтение. Фикстуры — `engine/tests/fixtures/meeting-v<N>/`, тест `engine/tests/test_data_schema.py`.
- Набор моделей версионируется отдельно (`version` в манифесте моделей, `scripts/models_manifest.py` поднимает его при смене списка). При обновлении докачиваются только изменившиеся файлы: файл с той же суммой SHA-256 берётся из кэша Hugging Face (`blobs/<sha256>` или прежний снапшот) жёсткой ссылкой после сверки размера и суммы (`model_store.reuse_unchanged`).

## Первая установка и карантин

**Основной путь — установщик одной командой**, без окна Gatekeeper:

```bash
curl -fsSL https://tonyprots.github.io/mostik/install.sh | bash
```

`scripts/install.sh` читает ту же ленту, что Sparkle, качает `.dmg` из Releases через `curl` (он не ставит карантин), сверяет длину, проверяет `codesign --verify --deep --strict` и требование подписи `identifier "app.mostik.mac" and certificate leaf = H"<SHA-1>"`. Отпечаток зашит в сам скрипт, а не берётся из ленты: подменённая лента его не поменяет. Не совпало — не ставится ничего. Ставит в `/Applications` (нет прав — в `~/Applications`), запущенный Mostik не трогает. `publish-release.sh` кладёт скрипт в `gh-pages` рядом с лентой и перед этим сверяет отпечаток и адрес ленты с `release/release.conf`. Проверено на локальной ленте: установка, повтор поверх, испорченный образ и ad-hoc сборка (оба отвергнуты).

**Запасной путь — `.dmg` из браузера.** Самоподписанный `.dmg` Gatekeeper при первом открытии не пускает: «Не удаётся проверить разработчика». На macOS 15 Sequoia правый клик → «Открыть» больше не помогает. Путь для пользователя (он же в `README.md` и в тексте каждого релиза, `release/release-notes.md`):

1. Перетащить Mostik в «Программы», открыть — macOS откажет.
2. «Системные настройки» → «Конфиденциальность и безопасность» → внизу «Mostik заблокирован…» → **«Всё равно открыть»** → пароль.
3. Открыть Mostik ещё раз и выдать разрешения.

Это нужно один раз. Обновления Sparkle скачивает сам, через `NSURLSession` в процессе Mostik, а не браузером, и снимает с них карантин (`com.apple.quarantine`), поэтому Gatekeeper второй раз не спрашивает. Проверено `scripts/update-e2e.sh`: на установленной обновлением копии атрибута карантина нет.

## Выпуск по шагам

```bash
# 0. Один раз: сертификат «Mostik Release» и SHA-1 в release/release.conf, резервная копия, репозиторий.
# 1. Проверить конвейер без сертификата — ad-hoc .dmg «только для этой машины».
MOSTIK_RELEASE_OUT=/tmp/mostik-release scripts/release.sh --adhoc
# 2. Проверить цепочку обновления целиком на временном сертификате (~10 минут, ничего не публикует).
scripts/update-e2e.sh
# 3. Выпуск: версия — в Resources/Info.plist или VERSION=…, раздел версии — в CHANGELOG.md.
scripts/release.sh
# 4. Сухой прогон публикации, затем публикация.
scripts/publish-release.sh 0.1.0
scripts/publish-release.sh 0.1.0 --publish
```

Результат `release.sh` — в `release-out/`: `Mostik-<версия>.dmg`, `.dmg.sparkle-signature`, `appcast.xml`. Держать `release-out/appcast.xml` между выпусками: в нём история версий. Номер сборки (`CFBundleVersion`) по умолчанию — число коммитов и только растёт: Sparkle сравнивает именно его.

Проверить требование подписи установленного Mostik: `codesign -d -r- /Applications/Mostik.app` — должно быть `identifier "app.mostik.mac" and certificate leaf = H"<SHA-1 из release.conf>"`.

Первая сборка с настоящей лентой попадает к людям только из `.dmg`: копии ad-hoc о ленте не знают и сами не обновятся.

### Пробный выпуск и `update-e2e.sh`

`scripts/update-e2e.sh` проверяет цепочку без настоящего сертификата и без сети: временная связка ключей в `/tmp/mostik-e2e` (на время прогона — в списке поиска: иначе `codesign` её не видит; в конце список возвращается дословно, связка удаляется), в ней временный самоподписанный «Mostik Release» на 2 дня, временный ключ EdDSA из файла; два выпуска `release.sh` в пробном режиме (`MOSTIK_TEST_RELEASE=1`: лента и `.dmg` только на `http://127.0.0.1:<порт>`, `SUPublicEDKey` — временный, образ `Mostik-<версия>-test.dmg`); лента на локальном `http.server`. Проба `scripts/update-probe/main.swift` — настоящий Sparkle и настоящий `SparkleUpdateGuard` — обновляет копию 0.1.0 в `/tmp`. Сам Mostik не запускается. Проверки:

1. испорченный байт в `.dmg` — Sparkle не ставит (EdDSA);
2. лента изменена после подписи — отвергнута (`SURequireSignedFeed`);
3. в ленте другое требование подписи, лента подписана верно — отказ `SparkleUpdateGuard` с объяснением;
4. честное 0.1.0 → 0.1.1 ставится, требование подписи до и после одно и то же, карантина нет, `codesign --verify --deep --strict` проходит.

Sparkle пишет служебные ключи `SU*` в домен `app.mostik.mac` и кэш в `~/Library/Caches/app.mostik.mac`: скрипт удаляет только то, чего не было до него.

### Живая проверка разрешений (руками, один раз после появления сертификата)

Тест сохранения разрешений TCC автоматом не сделать: выдать разрешение может только человек. Порядок:

1. `VERSION=0.1.0 scripts/release.sh`, поставить `Mostik-0.1.0.dmg` в «Программы» вместо текущего Mostik (сборка ad-hoc теряет разрешения при смене подписи — это ожидаемо, один раз), пройти «Всё равно открыть».
2. Выдать все четыре разрешения: микрофон, Универсальный доступ, «Запись экрана», звук системы. Продиктовать фразу, записать короткую встречу — всё работает.
3. Опубликовать 0.1.0 (`publish-release.sh 0.1.0 --publish`), затем собрать и опубликовать 0.1.1 — хоть с одной строкой в `CHANGELOG.md`. Настоящая лента — единственный честный путь: подмена `SUFeedURL` проверяла бы другую сборку.
4. В Mostik: меню → «Проверить обновления…» → «Установить». Mostik перезапустится.
5. «Системные настройки» → «Конфиденциальность и безопасность»: Mostik стоит во всех четырёх списках, галочки включены, дублей нет. Продиктовать и записать встречу без новых запросов. `codesign -d -r- /Applications/Mostik.app` — то же требование, что в шаге 1.

## Ad-hoc образ — только для этой машины

`scripts/release.sh --adhoc` собирает `Mostik-<версия>-local-only.dmg`. Это проверка конвейера и «чистой машины», не выпуск, и раздавать такой образ нельзя:

- приложение подписано ad-hoc с требованием «только идентификатор» (`designated => identifier "app.mostik.mac"`). Иначе macOS забывала бы разрешения после каждой пересборки. Но то же требование выполнит любой бинарник, подписанный ad-hoc с идентификатором `app.mostik.mac`, и TCC отдаст ему микрофон, запись экрана и Универсальный доступ, выданные Mostik;
- без подписи Sparkle и без ленты; ключ EdDSA в этом режиме не читается;
- на другой машине Gatekeeper пустит его только через «Всё равно открыть».

**Подмена ad-hoc сборки закрывается самоподписанным сертификатом:** требование выпуска — `certificate leaf = H"<SHA-1>"`, его выполнит только код, подписанный закрытым ключом «Mostik Release». Остаток: без hardened runtime проверки библиотек нет, и код, подгруженный в процесс Mostik (`DYLD_*` от того же пользователя), работает с его разрешениями. Ad-hoc сборки разработчика по-прежнему с требованием «только идентификатор».

## Принятые риски

Общий знаменатель: процесс того же пользователя может многое и без Mostik — переписать `~/.zshrc`, `~/Library/LaunchAgents`, `/opt/homebrew`. От него Mostik не защищается; от других учётных записей и от `launchctl setenv` — защищается. Каждый пункт пересматривается при переходе на Developer ID.

- **Отпечаток команды хука в связке ключей.** Mostik принимает только свою запись `app.mostik.mac.hooks` и только из связки «Вход» (путь — по домашней папке из `getpwuid`, не из `$HOME`): расшифровка в ACL разрешена ровно ему (`KeychainItemOwnership`, `HookDigestReader`), запись чужого бинарника — «чужая» или «не прочесть», хук тогда выключен и Mostik спрашивает. Остаток: код внутри самого процесса Mostik пишет запись как Mostik; запись, которую чужой бинарник закрыл от Mostik, удаляется только руками в «Связке ключей»; скрипт, который зовёт команда, в отпечаток не входит — это файл пользователя. Команда исполняется `/bin/zsh -fc`, без `~/.zprofile` и `~/.zshrc`. Подмена самого `login.keychain-db` шумная (пропадают все пароли) и без Developer ID не закрывается.
- **Метка облачного согласия `claude@v1`.** Метка — публичная константа: она ловит случайный `settings.json` (старый или чужой файл), а не умышленную правку. К связке ключей не привязана: запись ad-hoc привязана к `cdhash`, и согласие сбрасывалось бы при каждой пересборке. Согласие разрешает отправлять текст в Anthropic, но не запускает код; встречи «только на этом Mac» в облако не уходят и с согласием. С Developer ID согласие можно хранить по схеме хука.
- **Universal Clipboard.** Вставка через буфер обмена не помечена `.currentHostOnly`, поэтому на долю секунды текст может стать доступен другим устройствам Apple той же учётной записи.
- **Программы из папок, куда пишет пользователь.** `ffmpeg` и `ffprobe` (из Homebrew; свои WAV встречи transcriber читает без них, встроенным Python — `audio.native_wav`, они нужны только для импорта файлов других форматов), `tmux` (адресная вставка) и `claude` (после согласия на облако) запускаются из фиксированного списка мест, `PATH` в выпуске системный. `ffmpeg` и `ffprobe` движок перед прогоном проверяет: файл и папка принадлежат пользователю или root и не открыты на запись другим (`meeting.check_media_tools`, иначе отказ `media_tool_untrusted`). Подписей у этих сборок нет, сверять не с чем. `tmux` получает урезанное окружение без `TMUX_TMPDIR`; сервер со своим `TMUX_TMPDIR` Mostik не видит, текст уходит обычной вставкой ⌘V.
- **`fluidaudiocli`.** Бинарник ищется только внутри бандла и сверяется по сумме (`docs/packaging.md`, «Цепочка поставки»). Сам он качает модели с huggingface.co, если набора нет, и `HF_HUB_OFFLINE` не читает. Поэтому Mostik не зовёт его без полного набора моделей (`fluid_offline.models_problem`), `MODEL_REGISTRY_URL` и `REGISTRY_URL` в офлайновых окружениях указывают на закрытый порт `127.0.0.1:9`, голосовая память идёт под `sandbox-exec` без сети. Остаток: на встрече бинарник запускает копия transcriber без песочницы; если CoreML не загрузит модели, запрос на скачивание уйдёт на закрытый порт и упадёт.
- **Окружение дочерних процессов — белый список.** Движок, его дети, `git`, `ps`, `pdftotext` и `claude` получают только перечисленные переменные (`EngineEnvironment.allowlisted`, `isolation.child_env`/`tool_env`/`claude_env`); `DEVELOPER_DIR`, `SDKROOT`, `TOOLCHAINS` снимаются всегда. User site у transcriber отключён `PYTHONNOUSERSITE=1`. Остаток: в debug-сборке и при запуске движка из репозитория переопределения берутся из окружения; `claude` получает `ANTHROPIC_*` (в том числе `ANTHROPIC_BASE_URL`), `CLAUDE_CONFIG_DIR`, `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` и `NODE_EXTRA_CA_CERTS`, без них он не работает за корпоративным прокси. Отсюда смена адресата облака: кто может выставить окружение Mostik, тот может направить облачный текст на свой адрес или через свой прокси; согласие на облако при этом по-прежнему обязательно.
- **git мимо шима.** Шим `/usr/bin/git` можно увести подложенным кэшем xcrun, поэтому Mostik зовёт `$(xcode-select -p)/usr/bin/git` и только если вся цепочка до файла принадлежит root и не открыта на запись (`SafeGit.executable`, `project_glossary.git_executable`); иначе список файлов проекта строится обходом папки. `GIT_CONFIG_GLOBAL=/dev/null` не ставится: опасные ключи `~/.gitconfig` перекрыты аргументами `-c`. Вне Mostik шим по-прежнему вызывают `claude` и хук после встречи — это тот же класс, что и выше.
- **Кэш transcriber.** Встречи расшифровываются с `--no-cache`. То, что уже лежит в `~/.cache/transcriber` от прошлых расшифровок, Mostik не трогает: записи там стираются сами через 90 дней.
- **Поле пароля.** Mostik не записывает, если включён защищённый ввод или фокус — `AXSecureTextField`, и проверяет ещё раз в конце записи. Защищённый ввод — общий флаг системы: если его держит другое приложение, Mostik тоже не запишет и скажет почему. Поле, которое рисует себя само (часть Electron и игр), Mostik не узнает.
- **Команда «отправь».** Если текст прошёл модель, команда засчитывается, только если она есть и в сказанном до модели (`SpokenCommands`).
- **Брифы и сводки при пометке «только на этом Mac».** Собранные до пометки `briefs/` и `digests/` не пересобираются и не удаляются; MCP и CLI агентам их не отдают. Записано в `PRIVACY.md`.
- **Выключение голосовой памяти без стирания.** Встреча, которая в этот момент расшифровывается, новых отпечатков не пишет, накопленные остаются до «Забыть».
- **Мелочи до Developer ID:** `MOSTIK_SELFTEST*` в выпуске (запись фиксированного текста от того же пользователя); `SUFeedURL` из defaults Sparkle (установку держат `SURequireSignedFeed`, EdDSA и требование подписи в ленте); `release.sh` берёт `python3`, `git` и `xcrun` из `PATH` сборщика; нет сквозного теста офлайн-окружения собранного `.app`, офлайн проверен по частям.

## Известные ограничения

- Фон окна `.dmg` проверен по структуре (`.DS_Store` разбирается, alias на месте), но не глазами: у сессии нет разрешения на снимок экрана. Закладки `pBBk` нет (в ней был путь к образу на машине сборщика), Finder берёт фон из alias-записи `icvp.backgroundImageAlias`. Перед первым выпуском открыть `.dmg` и посмотреть; если фона нет — писать минимальную закладку, собранную на томе образа в `/tmp`, и снова прогнать проверку образа.
- В тёмной теме Finder рисует подписи значков белым поверх светлого фона, они плохо читаются. Так у большинства `.dmg`; если мешает — сделать фон средней яркости.
- Python лежит в `Contents/Resources/python`. Apple советует держать код в `Contents/MacOS` или `Contents/Frameworks`; нотаризация такое обычно принимает, но если `notarytool log` пожалуется, перенести Python в `Contents/Frameworks`.
- Цепочка обновления проверена на временном сертификате и временном ключе EdDSA из файла (`scripts/update-e2e.sh`). Не проверены: подпись ключом EdDSA из связки (`--account`) на настоящей ленте, Pages и Releases вживую, сохранение разрешений TCC после обновления (шаги — «Живая проверка разрешений»), стандартные окна Sparkle в настоящем Mostik (проба ведёт Sparkle своим драйвером без окон).
